# sub-lab

Сервис зеркалирует подписки, конвертирует форматы (`raw`/`yml`), хранит короткие ссылки, пользователей и сессии в SQLite, и отдает UI (главная, `/admin`, публичная страница `/l/:id`).

В контейнере запускаются:
- Node.js API/UI (`8788`)
- встроенный subconverter (`8787`)

## Что умеет
- Получение подписки с конвертацией (`/sub`).
- Выдача последней успешной версии из кэша (`/last`).
- Короткие ссылки `/l/:id` с публичной страницей подключения.
- Публичные API для страницы шаринга:
  - `/api/public-short-links/:id`
  - `/api/public-short-links/:id/meta`
- Каталог приложений и гайды:
  - `/api/apps`
  - `/api/apps/guide?app=...&os=...`
- Авторизация и роли account (`viewer`/`editor`/`admin`), админка `/admin`.
- Статистика `/stats`: обращения по дням, устройства, разрезы по ОС и приложениям.
- Favorites, mock-sources, профильный редактор.

## Мобильный клиент

В `mobile/` лежит Android-клиент с двумя ядрами — Xray и Mihomo — и
переключателем между ними. Сборка и устройство описаны в
[`mobile/README.md`](mobile/README.md).

## Роли и интерфейс

Роль приходит из account (группа `sub_mirror_*`) и определяет и то, что видно в
интерфейсе, и то, что примет сервер.

| Роль | Что видит |
| --- | --- |
| `viewer` | Только список подписок: свои и выданные ему. Скопировать ссылку и открыть страницу подключения. Ничего не создаёт и не меняет. |
| `editor` | Свой список, короткая форма добавления и изменения: название, источник, формат, ОС, приложение. Резервная копия и восстановление. |
| `admin` | Всё вышеперечисленное плюс полный конструктор (короткая ссылка, теги, скрытие, режим серверов, группы Clash, профили, HWID), массовый импорт, объединение, тест приложения, overrides, устройства подписки, выдача доступов и `/admin`. |

Подписка, выданная через доступ к короткой ссылке, появляется в списке сама и
помечается «выдана вам»: она не хранится в списке получателя, а собирается на
каждый запрос, поэтому отзыв доступа убирает её сразу.

Страница подключения `/l/:id` остаётся публичной: вход для неё не требуется ни
на какой роли.

## Переезд с sub-mirror

Сервис переименован. Внутри контейнера всё переносится само:

- `sub-mirror.sqlite` переименовывается в `sub-lab.sqlite` при первом старте
  (вместе с `-wal` и `-shm`);
- прежние имена переменных окружения (`SUB_MIRROR_DATA_DIR`,
  `SUB_MIRROR_HOST_PREFIX`, `SUB_MIRROR_LOCAL_PORT`) продолжают работать как
  запасной вариант;
- избранное в браузере переносится со старого ключа `localStorage`.

Что нужно сделать руками на хосте — каталоги тома переименовались в
`docker-compose.yml`:

```bash
sudo mv /srv/homeapps/sub-mirror /srv/homeapps/sub-lab
sudo mv /opt/homeapps/sub-mirror /opt/homeapps/sub-lab
mv ~/projects/sub-mirror ~/projects/sub-lab
docker compose rm -sf sub-mirror
```

Ключ приложения в account остался `sub_mirror`: группы в LLDAP называются
`sub_mirror_admin`, `sub_mirror_editor`, `sub_mirror_viewer`, и переименовывать
их не требуется.

Cookie сессии сменила имя на `sub_lab_session`, поэтому после обновления
потребуется войти заново.

### Внутренняя модель и параметр `nodes`

Подписка разбирается не в плоский список серверов, а в список **записей**
(`normalized-v2`, `app/model/`). Запись — это одна строка списка в приложении:
один конфиг JSON-бандла Xray, один прокси Clash, одна ссылка raw. Всё, что
провайдер держит внутри записи — кандидаты балансировщика, мосты, loopback,
`routing`, `dns`, `observatory` — остаётся внутри записи и не всплывает
отдельными серверами.

Каждая запись хранит исходный объект целиком (`entry.native`), поэтому
обратная конвертация в исходный формат отдаёт подписку без потерь.

`nodes` управляет только теми форматами, где вложенности нет:

| значение | что попадает в `raw` / `clash` |
| --- | --- |
| `collapse` (по умолчанию) | один узел на запись — представитель: цель маршрута по умолчанию, а при балансировщике самый дешёвый кандидат |
| `group` | представитель и кандидаты того же балансировщика; в Clash запись становится своей `url-test` группой |
| `expand` | каждый прокси-outbound отдельным сервером |

Обратная конвертация (`json` → `json`, `yml` → `clash` без правок) отдаёт
сохранённый исходник и `nodes` не учитывает.

Пример на реальной подписке из 10 конфигов Xray:

```bash
curl ".../sub?output=raw&sub_url=..."               # 10 строк
curl ".../sub?output=raw&nodes=group&sub_url=..."   # 13 строк
curl ".../sub?output=raw&nodes=expand&sub_url=..."  # 122 строки
```

### Короткие ссылки
- `POST /api/short-links` (auth)
- `GET /api/short-links/:id` (auth)
- `PUT /api/short-links/:id` (auth)
- `DELETE /api/short-links/:id` (владелец или админ) — сносит ссылку вместе с
  доступами, устройствами, историей, лимитами и счётчиками. Не то же самое, что
  «убрать из своего списка»: адрес перестаёт отвечать у всех. Админ так удаляет
  и чужие подписки — из своего списка их убрать нельзя, их там нет.
- `GET /api/short-links/health` (auth) — итоги суточных проверок по всем
  доступным подпискам. Отдельной ручкой: список карточек не должен ждать.
- `POST /api/short-links/:id/health` (доступ на просмотр) — проверить сейчас.
- `GET /l/:id` (public resolve)

Если устройство заблокировано или уперлось в лимит, короткая ссылка не отдаёт
ошибку транспорта: приложение получает валидную подписку из **одного** сервера,
имя которого — текст из политики (`blockedMessage` / `limitMessage`), а адрес,
порт и ключи случайные и заведомо неживые (`203.0.113.0/24`, документационная
сеть). Человек читает причину прямо в списке серверов клиента. Браузеру
(`Accept: text/html`) вместо этого показывается HTML-страница с тем же текстом.

Ссылка с заданным `maxUsers` требует hwid: без него устройство не посчитать, и
лимит обходился бы одним запросом. Запрос за конфигом без hwid получает
HTML-страницу с текстом `blockedMessage`; страница подключения `/l/:id` в
браузере при этом продолжает открываться.

`/l/:id` поддерживает query override:
- `?type=raw`
- `?type=yml`

Это переопределяет `output` для резолва короткой ссылки.

### Объединение подписок
Объединение живёт отдельным источником `merge:<id>` и собирается из других
подписок. Устройство, приложение и профиль у каждого источника свои — в
объединении настраивается только состав и отбор серверов.

- `POST /api/merged-sources` — создать объединение (editor).
- `GET /api/merged-sources/:id` — состав объединения (editor).
- `PUT /api/merged-sources/:id` — пересобрать состав. Идентификатор не меняется,
  поэтому адрес подписки у пользователей остаётся прежним.
- `POST /api/merged-sources/preview` — имена серверов каждого источника; окно
  объединения применяет регулярку к ним локально, без похода в сеть на каждый
  введённый символ.

Элемент объединения — параметры источника плюс `filter`:

```json
{ "sub_url": "https://example.com/sub", "output": "raw",
  "filter": { "pattern": "whitelist|бел[ыо]|обход", "onEmpty": "all" } }
```

- `pattern` — регулярка по имени сервера, регистр не учитывается. Пусто — берём
  все серверы источника. Некорректный шаблон не валит подписку: отбор просто не
  применяется.
- `onEmpty` — что делать, если под регулярку не подошло ничего: `all` (по
  умолчанию — взять все серверы источника), `skip` (источник не попадёт в
  объединение) или `error` (подписка вернёт ошибку, так сразу видно, что
  регулярка устарела).

Одинаковые имена серверов разводятся номерами (`NL Амстердам`, `NL Амстердам (2)`):
в приложении две одинаковые строки неразличимы, и непонятно, какая из какой
подписки. Адрес и ключи при этом не меняются — только подпись.

Заголовки источников сводятся в один ответ: `subscription-userinfo` суммирует
`upload`, `download` и `total`, а `expire` берётся ближайший — когда кончится
первый источник, часть серверов объединения перестанет работать. Безлимитный
источник делает безлимитным и общий `total`. `profile-update-interval` —
минимальный из заявленных, `profile-title` — название объединения (не-ASCII
уезжает в `base64:`, как это делают провайдеры).

### Пинг серверов
- `POST /api/ping` — замер задержки до серверов подписки (auth).

Тело: либо `params` с параметрами подписки (панель сама сходит за источником и
разберёт серверы), либо готовый список `targets` (`{host, port, sni, name}`).
Дополнительно: `mode` (`tcp` по умолчанию, `tls`, `dns`), `attempts` (1…5),
`timeoutMs` (300…10000).

Меряется то же, что меряет телефон до поднятия туннеля: разрешение имени,
TCP-рукопожатие и TLS. Клиента протоколов у панели нет, поэтому это оценка
доступности точки входа и расстояния до неё, а не скорость внутри туннеля. И
замер идёт от сервера панели, а не из сети пользователя.

### Статистика
- `GET /api/stats?days=30` — сводка по подпискам, которые видит текущий пользователь
  (admin считает всю панель, остальные — свои ссылки и выданные им доступы).
  `days` принимается в диапазоне 7…180.

Ответ содержит:
- `totals` — подписки, устройства, активные за сутки/неделю/месяц, обращения;
- `daily` — по дням: обращения и новые устройства;
- `byOs` / `byApp` — разрез устройств по последнему визиту;
- `topLinks` — подписки по числу обращений за период;
- `recentDevices` — последние подключения.

Обращения копятся в таблице `short_link_daily_hits` (счётчик растёт при резолве
`/l/:id`), поэтому график заполняется начиная с обновления — прошлые обращения в
посуточном разрезе не восстанавливаются, общий `hits` при этом сохраняется. В
sync-bundle посуточные счётчики не входят: они считаются локально для каждой
панели.

### Auth и admin
- `GET /api/auth/me`
- `POST /api/auth/login` — возвращает ссылку на вход в account
- `POST /api/auth/logout`

Пользователи, пароли и роли живут в account; здесь они только читаются.
Роль берётся из `access.sub_mirror` (ключ приложения в account остался
прежним — так называются группы в LLDAP).

Cookie сессии в браузере — `sub_lab_session` (`SESSION_COOKIE`), а не общая
`kartoteka_session`: cookie не разделяются по портам, и с общим именем вход в
соседнее домашнее приложение подменял пользователя здесь. Имя cookie для
внутреннего API account задаётся отдельно — `ACCOUNT_SESSION_COOKIE`.
- `GET /api/admin/users` (admin)
- `POST /api/admin/users` (admin)
- `PUT /api/admin/users/:username` (admin)
- `DELETE /api/admin/users/:username` (admin)

Ограничения безопасности:
- нельзя удалить текущего admin.
- нельзя сменить роль текущего admin самому себе.

### Синхронизация панелей
Machine-to-machine API включается только если задан `SYNC_API_TOKEN`.

- `GET /api/sync/export` — экспорт данных, требует `Authorization: Bearer <SYNC_API_TOKEN>` или `X-Sync-Token`.
- `POST /api/sync/import` — импорт bundle, требует admin-сессию или sync token.
- `POST /api/sync/pull` — текущая панель забирает export с другой панели и импортирует его.

Экспорт не включает пароли и auth-сессии. Синхронизируются короткие ссылки, доступы, favorites, лимиты пользователей, seen-users/history, override-данные и editable profiles.

Пример pull с `99.21` из панели `sub.nl.cdn6.ru`:
```bash
curl -X POST "http://192.168.99.21:25500/api/sync/pull" \
  -H "Authorization: Bearer $SYNC_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"remoteUrl":"https://sub.nl.cdn6.ru"}'
```

#### Подключённые установки (админка → «Синхронизация»)

Разовая настройка вместо curl: адрес удалённой панели и её `SYNC_API_TOKEN`
сохраняются в таблице `sync_peers`, дальше изменения приезжают по кнопке или по
расписанию. Связь односторонняя — тянет только та панель, где заведён пир;
удалённая о нём не знает, ей достаточно отдавать `/api/sync/export`.

- `GET /api/sync/peers` — список; токен наружу не отдаётся, есть только `hasToken`.
- `POST /api/sync/peers` — завести (`remoteUrl`, `remoteToken`, `intervalMinutes`, `includeProfiles`).
- `PUT /api/sync/peers/:id` — правка. Пустой `remoteToken` означает «оставить прежний».
- `DELETE /api/sync/peers/:id` — отключить; загруженные данные остаются.
- `POST /api/sync/peers/test` — проверка связи без импорта, принимает `id` либо пару `remoteUrl`/`remoteToken`.
- `POST /api/sync/peers/:id/pull` — прогон; `{"dryRun":true}` только смотрит.

Прогон идёт в обе стороны: сначала забираем выгрузку удалённой панели и
накатываем у себя, затем, если у пира включена досылка (`pushEnabled`,
по умолчанию да), отправляем свою выгрузку в её `/api/sync/import`. Инициатива
всё равно только наша — удалённая панель ничего не запускает. На `dryRun`
досылка тоже выполняется, но с `dryRun` на той стороне: так проверка ловит
неверный токен или упёршийся лимит тела, ничего не записывая.

Все шесть требуют admin-сессию. Расписание проверяется раз в минуту, интервал
считается от последней попытки — упавший пир не долбится на каждом тике.

### Ссылки Happ (crypt5)

Формат `happ://crypt5/...` разбирается и собирается своим кодом в
`app/happ-crypt5.js` — без внешнего бинарника, поэтому работает на любой
платформе и в обе стороны.

- `POST /api/happ-decrypt` — `{subUrl}` → обычная ссылка.
- `POST /api/happ-encrypt` — `{url, marker?, salted?}` → `happ://crypt5/...`.
  Требует роль редактора.

Таблица ключей — `resources/happ/crypt5-keys.json` (36 маркеров, публичная
таблица протокола из `LeeeeT/happ-decryptor`). Путь переопределяется
переменной `HAPP_CRYPT5_KEYS`; в образе файл лежит в `/resources/happ`.

Ключ шифрования разовый, поэтому одна и та же подписка каждый раз даёт новую
строку — это нормально, все они ведут на один адрес. Маркер берётся из той же
таблицы: приложение узнаёт ссылку по нему, свой выдумать нельзя.

Node с 18.19 запрещает `RSA_PKCS1_PADDING` на приватной расшифровке
(атака Marvin), поэтому блок снимается сырым и PKCS#1 v1.5 разбирается вручную.

### Проверка подписок

Раз в час планировщик добирает ссылки, которых не проверяли больше суток, и
ходит к провайдеру по сохранённым параметрам — последовательно, с паузой
750 мс: одновременный залп по двум десяткам провайдеров выглядит ровно как то,
от чего они ставят антибот.

Живой подписка считается, если из ответа удалось достать хотя бы один сервер:
200 с пустым телом или страницей защиты — это не «жива». Ответ приводится к raw
тем же `produceOutput`, поэтому одинаково разбираются base64, clash и json, а
на HTML-заглушке в `error` попадает внятная причина.

Обрыв связи с нашей стороны (таймаут, DNS, отказ соединения) записывается как
`unreachable`, а не как «подписка мертва»: иначе разовая авария у нас красит
весь список в красное на сутки. Прошлые цифры при этом сохраняются, а
перепроверка таким ссылкам назначается через час, а не через сутки.

Итог — одна строка на ссылку в `short_link_health`: срок из
`subscription-userinfo`, трафик, `support-url` и `profile-web-page-url` для
кнопки «продлить». Объединения не проверяются: они ходят сразу в несколько
источников, каждый из которых проверяется сам по себе.

Проверки синхронизируются между панелями по `checked_at`: ходить к провайдеру
дважды с двух установок незачем, ответ будет тот же.

### Удаление и синхронизация

`DELETE /api/short-links/:id` оставляет надгробие в `deleted_short_links`.
Без него удаление не доезжало бы до второй панели, а оттуда ссылка возвращалась
бы назад при следующем обмене.

Надгробия едут в выгрузке и применяются первыми, до списка ссылок. Правило —
кто новее, тот и прав: если локальная ссылка правлена позже удаления, значит её
завели заново и надгробие устарело; если раньше — ссылка удаляется, а надгробие
оседает и едет дальше. Создание ссылки с тем же идентификатором надгробие
снимает.

### Счётчики просмотров и несколько установок

Каждая установка при первом обращении заводит себе `installation_id`
(таблица `app_meta`). Просмотры пишутся с этой пометкой:

- `short_link_daily_hits (short_link_id, day, origin, hits)` — посуточно;
- `short_link_hit_totals (short_link_id, origin, hits)` — всего.

Статистика складывает строки всех установок. Импорт чужой выгрузки берёт
`MAX` по каждой паре «ссылка + установка» и пропускает строки со своим
origin, поэтому повторный обмен ничего не удваивает, а старая выгрузка не
откатывает счётчик назад. Столбец `short_links.hits` остался локальным
счётчиком и при импорте не трогается.

Установки, заведённые до этого, переносят накопленный `short_links.hits` на
свой origin один раз — при первом обращении к идентификатору.

### Чужие подписки у админа

`GET /api/favorites` доклеивает администратору все короткие ссылки установки,
которых нет в его списке: `derived: true` (чтобы запись не осела у него при
сохранении), `foreign: true` и `ownerUsername`. Остальным ролям эта часть
не отдаётся вовсе. В интерфейсе они спрятаны за фильтром «Доступные мне»,
который стоит по умолчанию, и помечены бейджем с логином владельца.

  по портам.

  (`kartoteka_session`), общее для всех приложений.
- `ACCOUNT_URL`, `ACCOUNT_SERVICE_TOKEN` — внутренний API account.
- `SUB_LAB_HOST_PREFIX`, `SUB_LAB_LOCAL_PORT` — как вычислять свой адрес и адрес account.

### Отдельный сервер: sub-lab + account + lldap
`deploy/` ставит весь стек целиком на чужую машину — панель, вход и каталог
пользователей. Скрипты на Python: деплой запускают с Windows, где нет ни
`rsync`, ни `sshpass`.

```bash
python -m pip install paramiko

# первая установка: спросит адрес, домены и пароль, напомнит про DNS
python deploy/first-deploy.py

# дальше — обновления по короткому имени цели
python deploy/update.py vps
python deploy/update.py vps --with-data   # ещё и перелить данные с 99.20
python deploy/update.py vps --cert        # досоздать сертификаты
python deploy/update.py --list            # какие цели известны
```

Первый деплой: проверяет A-записи обоих доменов (и ждёт, пока их добавят),
доставляет docker, compose v2, nginx и certbot, переносит данные и секреты с
домашнего сервера, поднимает контейнеры, настраивает vhost'ы и сертификаты.
Параметры сервера сохраняются в `deploy/targets.local.json` — он в `.gitignore`,
потому что хранит пароль.

Что стоит знать:

- **Домена нужно два** — панель (`sub.…`) и вход (`account.…`) в одной зоне.
  Адрес входа выводится заменой первой метки домена панели, поэтому
  `sub.nl.example.ru` уводит на `account.nl.example.ru`, и никак иначе.
- **Секреты едут вместе с данными.** Каталог LLDAP зашифрован `LLDAP_KEY_SEED`,
  со свежесгенерированным он не прочитается, поэтому пять ключей из
  `/opt/homeapps/.env` переносятся как есть.
- **Кэш переносится тоже.** Ссылки с `endpoint=last` отдают последнюю удачную
  версию именно из него и без кэша отвечают 404.
- **lldap наружу не публикуется** — только `127.0.0.1:17170`.
- **Нужен compose v2.** v1 на свежих Docker падает с `KeyError: 'ContainerConfig'`
  при пересоздании контейнера с томами; `first-deploy.py` ставит v2 сам.
- Заливка кода **не удаляет** `sub-lab/resources`, а чистит его изнутри: этот
  каталог примонтирован в контейнер, и после `rm -rf` контейнер остался бы
  смотреть на удалённый inode — подписки начали бы падать с `profile not found`.
